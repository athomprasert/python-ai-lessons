Lesson 49 · Agent Fabric · MuleSoft

Build an Agent Broker

A hands-on build. Part A — author the broker's routing logic as an Agent Script graph. Part B — deploy it to CloudHub 2.0 and govern it with the Omni Gateway in Anypoint. You'll scaffold both yourself from TODOs; I won't hand you a finished file. Grounded entirely in public MuleSoft & Agentforce docs.

TL;DR — the two layers are complementary, not two versions
A working broker needs both halves: you author the orchestration as a graph in Agent Script (.agent files, edited in Anypoint Code Builder), and you deploy & govern it in Anypoint (publish to Exchange → CloudHub 2.0 → Omni Gateway policies). Part A is the "what it does"; Part B is the "where it lives and how it's controlled." Forget "v1/v2" — that was never a real product choice.

What you're building

A broker is "an intelligent routing service that coordinates task delegation across A2A-compliant agents." You'll build one that sits in front of the A2A agents you already made in L48 / L47 and routes an incoming request to the right one.

# The target: a broker routing to your existing agents caller (A2A request) │ ═══ OMNI GATEWAY ═══ # Part B: auth, rate-limit, policy, telemetry │ AGENT BROKER ◀── your .agent graph # Part A: which agent handles this? ├──▶ order-agent # (your L47/L48 A2A agents) └──▶ billing-agent

Prerequisites

  • Anypoint Code Builder — the authoring tool for broker projects (VS Code-based, desktop or web).
  • At least one A2A-compliant agent to route to. Your L47/L48 agents qualify — the broker delegates over A2A.
  • An Anypoint Platform org with CloudHub 2.0 (or Runtime Fabric) for Part B.

Part A · Author the broker in Agent Script

A1 — Create the project skeleton

A broker project has a fixed shape (quoted from the Building Agent Networks guide). Create this yourself in Code Builder — MuleSoft ships "a YAML template and Agent Script file to give you a head start," so start from that template rather than a blank folder:

# Verified project layout — Building Agent Networks guide
my-agent-network-project/
├── exchange.json          # asset metadata for publishing to Exchange
├── agent-network.yaml     # the registry (which agents/MCP) + context (connections/policies)
└── brokers/
    └── broker1.agent      # the broker graph: trigger, nodes, edges
Two authoring paths — pick one
The release notes confirm two ways to author in Code Builder: (1) write the YAML/Agent Script by hand, or (2) use MuleSoft Vibes — "create and configure agent networks using natural-language prompts… including broker graph design, node configuration, and Exchange asset integration." Learn path 1 first (below) so you understand what Vibes generates; reach for Vibes to move fast once you do.

A2 — Register the downstream agents (agent-network.yaml)

Before the broker can route to an agent, the network has to know it exists. The agent-network.yaml has a registry section (the agents/MCP servers, defined locally or referenced from Exchange — "agent assets must be A2A-compliant") and a context section (connections and policies).

A3 — Write the broker graph (brokers/broker1.agent)

This is the heart of it. Verified rules from the guide:

  • "Define broker orchestration as a graph of nodes, edges, and triggers."
  • "All graphs must start on an A2A trigger" — that's your entry point.
  • Each node is either a probabilistic node ("complex, open-ended decisions that require nuanced judgment" — the LLM classifies intent) or a deterministic node ("enforce fixed execution paths once a key decision has been made" — the actual route).
  • Edges are the transitions between nodes, carrying input/output data.

So the smallest useful broker is: trigger → classify (probabilistic) → route (deterministic) → delegate. Your turn — build that graph from the scaffold:

# brokers/broker1.agent — STRUCTURE sketch, not verified syntax.
# The concrete keywords live in the reference — see the note below. Fill the TODOs.

# TODO(A3a): declare the A2A trigger — the required entry point of every broker graph.

# TODO(A3b): add a PROBABILISTIC node "classify_intent".
#   Job: read the incoming task and decide which agent should handle it.
#   This is the "nuanced judgment" the LLM is allowed to make.

# TODO(A3c): add a DETERMINISTIC node "route".
#   Job: given the classified intent, delegate to order-agent OR billing-agent.
#   No LLM freedom here — a fixed mapping. This is "guided determinism".

# TODO(A3d): add EDGES: trigger -> classify_intent -> route -> (delegate to chosen agent).

Read the graph like a switch with one AI-powered case selector: the probabilistic node is the part that decides which branch (like an LLM computing the switch key), and the deterministic nodes are the fixed branches that run once the key is set. The if @variables.x == True: conditional is your ordinary guard clause; transition to is a labelled jump.

Part B · Deploy & govern in Anypoint

Authoring gives you a graph; Part B makes it a running, governed service. Verified deployment flow from the guide:

  1. Publish assets to Exchange. Use MuleSoft Vibes to "publish the assets to Anypoint Exchange." A broker published to Exchange "become[s] reusable by other brokers" — that's the reuse story, same as any Exchange asset.
  2. Deploy to CloudHub 2.0. Push the agentic assets to CloudHub 2.0, "managed through Runtime Manager." (Runtime Fabric is the alternative target if you self-host.)
  3. Front it with a single Omni Gateway. The reference architecture shows "a single Omni Gateway for ingress and egress" — ingress to your broker, egress to external agents.
  4. Attach governance policies. Register your Agent, MCP, and LLM instances in API Management, then apply the applicable A2A, MCP, and LLM Omni policies. This is where auth and rate-limiting live — not in the broker graph.
  5. Observe. The Omni Gateway emits "logs, metrics, and traces" into Anypoint Monitoring — how you confirm routing actually happened.
The one distinction to keep straight
Part A (broker graph) decides which agent handles the task. Part B (Omni Gateway) enforces auth, rate limits, and policy around it. If you catch yourself putting rate-limit logic into a .agent node, stop — that belongs in an Omni policy in API Management.

Verify the whole thing end-to-end

  1. Send an A2A request that should go to order-agent; confirm in Anypoint Monitoring it was delegated there.
  2. Send one that should go to billing-agent; confirm the route changed.
  3. Hit it fast enough to trip your rate-limit policy; confirm the gateway (not the broker) rejected it.
"Building a broker is two moves, not one. First you author the routing as a graph — an A2A trigger, an LLM node that reads intent, deterministic nodes that lock the path once the decision's made. That's Agent Script in Code Builder, and you can even generate the first draft with natural language via Vibes. Second, you publish it to Exchange, deploy to CloudHub 2.0, and wrap it in a single Omni Gateway that handles auth, rate limits and telemetry. The graph decides who; the gateway governs the traffic. Same split as API-led: the logic and the governance are separate layers, and that separation is exactly what makes it enterprise-grade."

Check yourself

  1. Where does the broker graph's execution have to start, and why?
    Show answer
    On an A2A trigger — "all graphs must start on an A2A trigger." It's the entry point that receives the incoming A2A task the broker will route.
  2. You need the broker to pick between three agents based on the meaning of the request, then always run a fixed audit step. Which nodes?
    Show answer
    A probabilistic node for the pick ("complex, open-ended decision… nuanced judgment"), then a deterministic node for the audit step ("enforce fixed execution paths once a key decision has been made"). That's guided determinism.
  3. Rate-limiting the broker: which layer, and where do you configure it?
    Show answer
    The Omni Gateway, via an Omni policy in API Management — Part B. Never inside a .agent node. The graph decides routing; the gateway enforces traffic policy.
