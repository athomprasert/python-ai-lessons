Lesson 50 · Anypoint Studio · Object Store v2 + MuleSoft Vectors

Give your Mule agent memory: short-term with Object Store, semantic with Vectors

Take the tool-using agent from L44 and make it remember. You'll build two kinds of memory as visible Mule flow steps — a conversation buffer keyed by session, and a semantic recall store — so you see every read/write hop the Python frameworks hid from you.

What you'll build
A running Mule application that (1) remembers the last few turns of a conversation per sessionId using Object Store v2, and (2) recalls relevant facts from earlier — even across restarts — using the MuleSoft Vectors connector for semantic search. Same memory concepts every agent framework has (LangGraph checkpointer, CrewAI memory, ADK sessions) — but here each memory operation is an explicit, governable flow step, not a hidden framework feature.
Source honesty — read before you install
Two connectors here are versioned and evolving. Object Store is a long-stable core connector (operations: store, retrieve, contains, remove) — safe to rely on. The MuleSoft Vectors connector is part of the actively-evolving MuleSoft AI Chain (MAC) project; operation names, the embedding config, and store backends shift between releases. This lesson describes the shape of the flow — verify the exact operation names and config fields on Anypoint Exchange for the version you install. Screenshots you capture will be authoritative for your version.

Prerequisites

  • You've done L44 — the tool-using agent in Studio with the Inference connector. This lesson extends that project.
  • Anypoint Studio installed, and an Anypoint Platform account (needed to pull connectors from Exchange and to use Object Store v2 in the cloud).
  • An OpenAI API key (reused from L44) — the Inference connector uses it for both chat and embeddings.
  • A vector store for Part C. Easiest local option is a running PostgreSQL with the pgvector extension (Docker one-liner below). The Vectors connector also supports other backends — pick whatever your version lists.

Part 1 · The four kinds of agent memory

Before touching Studio, get the mental model. Every agent framework juggles some mix of these four. The names differ; the roles don't.

TypeWhat it holdsLifespanWe build it with…
Short-term / workingThe current conversation turns + scratchpadOne sessionObject Store v2 (Part B)
Long-term / episodicPast conversations — "what happened last time"Across sessionsa Database, or persisted Object Store
Semantic / knowledgeFacts & docs, retrieved by meaningPersistent, sharedMuleSoft Vectors (Part C)
ProceduralLearned rules — "always do X"Persistentsystem prompt / config
The one principle behind all of them
The agent stays stateless; state lives in an external store, keyed by a session or user ID. LangGraph does exactly this (a checkpointer saves graph state to Postgres/Redis by thread_id). CrewAI does it (SQLite + RAG). ADK does it (a managed Session/Memory service). MuleSoft's twist: the store is a system Anypoint already integrates with, and each read/write is a governed flow step — so you can log, secure, and monitor memory access like any other API call.
Frameworks give you memory primitives. Anypoint lets you turn any enterprise system — Redis, Postgres, Salesforce, a vector DB — into governed, reusable memory, and expose read/write as APIs your agents call safely. That's the positioning: not "MuleSoft is a better memory store," but "MuleSoft governs the memory you already have."

Part 2 · The shape of a memory-aware turn

Here's what one request looks like once both memories are wired. Read the flow of hops — you'll build each as a Mule component.

# One /ask turn with memory User # POST /ask { sessionId: "u-123", question: "..." } ↓ Object Store: retrieve(sessionId) # short-term: last N turns (or empty) ↓ Vectors: query(question) # semantic: top-k relevant past facts ↓ Build prompt: history + recalled + question ↓ Inference [Chat]: Answer Prompt # the LLM, now with context ├─ Object Store: store(sessionId, history+turn) # write short-term back └─ Vectors: add(question + answer) # write semantic memory ↓ Response { answer, sessionId }
Why this is the whole point of doing it in Mule
In L41 (Foundry threads) and L35 (AgentCore memory) the retrieve→augment→store cycle happened inside the platform — you passed a thread ID and trusted it. Here every arrow is a component you can click, log, and put a policy on. More steps, zero magic. That transparency is what an integration team wants when memory contains customer data.

Part B · Short-term memory with Object Store v2

New concept · Object Store
Object Store is Mule's built-in key/value store. You store a value under a key, retrieve it later, contains checks existence, remove deletes. Locally it's in-memory; on CloudHub, Object Store v2 is a managed, persistent, shared store — so your memory survives restarts and is shared across workers. We'll key each conversation by its sessionId, storing an array of turns. This is the Mule equivalent of LangGraph's checkpointer keyed by thread_id.
Steps:
  1. Open your mac-agent-demo project from L44. In the Mule Palette, click Search in Exchange and add Object Store Connector (asset objectstore). It's in the palette now.
  2. At the start of your /ask flow, right after the HTTP Listener, add a Transform Message that reads the incoming sessionId and question into variables:
    • vars.sessionId = payload.sessionId default "anon"
    • vars.question = payload.question
  3. Drag Object Store → Retrieve onto the flow. Set Key to #[vars.sessionId] and Default value to #[[]] (an empty array, so a brand-new session doesn't error). Set Target to history — the result lands in vars.history instead of overwriting the payload.
  4. Create a Persistent Object Store global config: in Global Elements → Create → Object Store, name it Conversation_Store, tick Persistent, and (optional) set an Entry TTL like 30 minutes so idle sessions expire. Point the Retrieve operation's Object store field at it.
  5. Now build the prompt with history. In the Transform that feeds the Inference [Chat] Answer Prompt operation, prepend vars.history to the messages before the new user question. (See the DataWeave in Part D.)
  6. After the LLM answers, add a second Transform that appends the new turn: vars.history ++ [{ role: "user", content: vars.question }, { role: "assistant", content: payload.response }] → into vars.updatedHistory. Optionally trim to the last 10 entries so the buffer stays small.
  7. Drag Object Store → Store. Key = #[vars.sessionId], Value = #[vars.updatedHistory], same Conversation_Store config. This writes the updated buffer back.
  8. Save. Read the XML tab to see the two operations Studio generated.

Local vs. CloudHub
Running locally, a "persistent" Object Store persists to disk under your Mule instance — fine for testing. The managed, shared, durable Object Store v2 only exists when you deploy to CloudHub. Don't promise a customer "memory survives across workers" until it's on CloudHub v2 — locally there's just one worker.

Part C · Semantic memory with the MuleSoft Vectors connector

New concept · Semantic memory = embeddings + a vector store
Short-term memory recalls turns by recency (the last N). Semantic memory recalls by meaning: you turn text into an embedding (a vector of numbers), store it, and later find the most similar stored vectors to a new query. That's exactly RAG from L07–L10 — reused here as long-lived agent memory. The MuleSoft Vectors connector wraps embed + store + similarity-search as flow operations, so you don't hand-code the vector math.
Spin up a local pgvector store
One Docker command gives you a Postgres with pgvector, so Part C runs locally: 
# Local vector store for testing
docker run -d --name pgvector -p 5432:5432 \
  -e POSTGRES_PASSWORD=mule \
  -e POSTGRES_DB=agentmemory \
  pgvector/pgvector:pg16
Then, in psql: CREATE EXTENSION IF NOT EXISTS vector;. The connector creates its own table/collection.
Steps:
  1. In the palette, Search in Exchange → add MuleSoft Vectors Connector (part of the MAC family). Confirm the exact asset name/version on Exchange.
  2. Create the connector's config. It typically needs two things:
    • an embedding model — point it at OpenAI with model text-embedding-3-small and your ${openai.api.key} property (same key file from L44);
    • a vector store — PGVector: host localhost, port 5432, database agentmemory, user postgres, password from a property. Set a store/collection name like agent_memory.
    Field names vary by version — match what your dialog shows.
  3. Write path. After the LLM answers (near your Object Store Store), add the Vectors add / ingest operation. Feed it the text to remember — e.g. vars.question ++ " → " ++ payload.response — plus metadata like { sessionId: vars.sessionId }. This embeds and stores the turn as durable semantic memory.
  4. Read path. Back near the start of the flow (after Object Store Retrieve), add the Vectors query / similarity-search operation. Input = #[vars.question], top-k = 3. Send the result to vars.recalled.
  5. In the prompt-building Transform, add a section using vars.recalled — e.g. a "Relevant things you remember:" block before the question. Now the LLM sees both recent turns and semantically-related older ones.
  6. Save and re-read the XML tab.

Short-term vs. semantic — when each earns its keep
Object Store (short-term) is cheap, exact, and recency-ordered — perfect for "what did we just say." Vectors (semantic) costs an embedding call per read and write, but recalls by meaning across sessions — "the user mentioned they're allergic to penicillin three weeks ago." Real agents use both: the buffer for the live conversation, the vector store for durable knowledge. Don't reach for vectors when a keyed lookup will do.

Part D · The DataWeave & XML (for reference)

The one piece worth seeing in full is the prompt-building Transform — it stitches all three memory sources into the messages array:

%dw 2.0
// Build the chat messages from: history (short-term) + recalled (semantic) + new question
output application/json
---
{
  messages: (
    // 1. system prompt (procedural memory — the standing rules)
    [{ role: "system", content: "You are a helpful assistant. Use remembered context when relevant." }]

    // 2. semantic recall, injected as context
    ++ (if (!isEmpty(vars.recalled))
          [{ role: "system",
             content: "Relevant things you remember:\n" ++ (vars.recalled map $.text joinBy "\n" ) }]
        else [])

    // 3. short-term buffer — the last N turns verbatim
    ++ vars.history

    // 4. the new user question
    ++ [{ role: "user", content: vars.question }]
  )
}

And the two Object Store operations Studio generates:

<!-- read at the start of the turn -->
<os:retrieve key="#[vars.sessionId]" objectStore="Conversation_Store" target="history">
  <os:default-value>#[[]]</os:default-value>
</os:retrieve>

<!-- write at the end of the turn -->
<os:store key="#[vars.sessionId]" objectStore="Conversation_Store">
  <os:value>#[vars.updatedHistory]</os:value>
</os:store>
Verify before quoting
The os:* operations above are stable. The Vectors add/query element names and attributes are not shown here on purpose — they change between MAC releases. Copy them from the XML tab of your Studio after you drop the operations, and paste them into the lesson if you want a permanent record.

Part E · Run and test the memory

The proof of memory is a two-request test — the second call should use what the first taught it.

Steps:
  1. Make sure your pgvector container is running and the OpenAI key is in config.yaml. Right-click the project → Run project. Wait for DEPLOYED in the console.
  2. Turn 1 — teach it: 
    curl -X POST http://localhost:8081/ask \
  -H "Content-Type: application/json" \
  -d '{ "sessionId": "u-123", "question": "My name is Attapol and I manage the SE team." }'
  3. Turn 2 — same session, test short-term: 
    curl -X POST http://localhost:8081/ask \
  -H "Content-Type: application/json" \
  -d '{ "sessionId": "u-123", "question": "What is my name?" }'
    It should answer "Attapol" — pulled from the Object Store buffer, not the model's training.
  4. Restart the app, then test semantic memory with a fresh session id: 
    curl -X POST http://localhost:8081/ask \
  -H "Content-Type: application/json" \
  -d '{ "sessionId": "u-999", "question": "Who leads the SE team?" }'
    The short-term buffer for u-999 is empty — but the Vectors query can still surface the earlier "manage the SE team" fact by meaning. That's semantic recall surviving a restart and crossing sessions.
  5. Watch the Studio console: you'll see the Retrieve, the Vectors query, the LLM call, then the Store and Vectors add — every memory hop logged in order.

Quiz

Test your understanding

  1. Why do we key the Object Store on sessionId instead of just storing one global history?
    Show answer
    So conversations don't bleed into each other. Every user (or chat) gets its own isolated buffer — the same reason LangGraph keys its checkpointer on thread_id. One global history would mix everyone's turns together.
  2. Turn 2 answered "Attapol" correctly. Did the LLM learn that?
    Show answer
    No — the model is stateless. We retrieved the stored history and put it back into the prompt before calling the LLM. The "memory" is the retrieve→augment→store cycle in the flow, not anything inside the model.
  3. When would short-term (Object Store) fail but semantic (Vectors) succeed?
    Show answer
    When the relevant fact is from a different session or was pushed out of the last-N buffer. Object Store recalls by key + recency; Vectors recalls by meaning across all stored turns, regardless of session or age.
  4. Why is "persistent" Object Store locally not the same as Object Store v2 on CloudHub?
    Show answer
    Locally it persists to one instance's disk — one worker, no sharing. Object Store v2 is a managed, durable, shared store across all CloudHub workers. Only the cloud version gives you memory that survives scaling and is consistent across replicas.
  5. Where does "procedural memory" live in this build?
    Show answer
    In the system prompt (and connector config) — the standing rules like "use remembered context when relevant." It's not stored per-session; it's the agent's fixed behavior. We didn't need a datastore for it.

Where to go from here

  • Deploy to CloudHub 2.0 and switch the Object Store to v2 — now memory is durable and shared across workers, monitored in Anypoint. That's the jump from "demo memory" to "production memory."
  • Add a summarization step: when the history buffer exceeds N turns, call the LLM to compress older turns into a summary before storing. This is exactly what LangGraph's summarizing checkpointers do (L22) — rebuild it as a Mule flow.
  • Put an API policy on the memory operations via API Manager — rate-limit writes, or require a scope to read another user's session. This is the governance angle no code-first framework gives you for free.
  • Expose read-memory and write-memory as MCP tools (see L46/L48) so other agents — Agentforce, Claude Desktop, the Python A2A agent from L47 — can share this governed memory store.
  • Compare memory models across the series: L28 ADK sessions, L35 AgentCore memory, L41 Foundry threads, and now Anypoint. Same four memory types, four platforms.
