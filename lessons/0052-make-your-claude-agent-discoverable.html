Make Your Claude Agent Discoverable & Governed

In L51 your Claude agent called MuleSoft tools. Now flip it: let other agents call your Claude agent — discovered through the MuleSoft Agent Registry and gated by Omni Gateway. Same agent, opposite direction.

One-line summary
A Claude Managed Agent is invoked over Anthropic's REST API — it has no Agent Card, so nothing in MuleSoft can see it yet. Give it an A2A front door (a task-listener that calls the Claude session API), register that card in the Agent Registry so peers can discover it, and publish the endpoint behind Omni Gateway so every inbound call is authenticated, rate-limited, and audited. The catch: the gateway only governs traffic that actually flows through it.

Why a Claude agent needs a front door

The Agent Registry (which lives in Anypoint Exchange) is A2A-native: it discovers agents by their Agent Card — the /.well-known/agent-card.json you built by hand in L47. But a Claude Managed Agent is invoked through Anthropic's sessions REST API; it doesn't serve an A2A endpoint and it publishes no card. So out of the box, nothing in MuleSoft can find it or route to it.

The fix is a thin A2A wrapper: a small service that speaks A2A on the outside and calls the Claude session API on the inside. That wrapper is what owns the Agent Card, gets registered, and sits behind the gateway.

Two hops, two auth layers — the part people get wrong

There are two separate security boundaries in that diagram, and they protect different things. Confusing them is the classic mistake.

Consumer ──[ ??? ]──► A2A wrapper ──[ x-api-key / TLS ]──► Anthropic agent ▲ ▲ YOUR responsibility Anthropic's REST auth (who is this caller? (proves the wrapper == your account) allowed? rate?)
  • Wrapper → Anthropic is handled by Anthropic: an x-api-key (or OAuth Authorization: Bearer) header over TLS, scoped to a workspace and a set of permissions. This authenticates your account to Anthropic — nothing more.
  • Consumer → wrapper is your job. Anthropic's key has no idea which of your users or downstream agents is calling; it can't rate-limit per consumer or audit who did what. That gap is exactly what Omni Gateway fills.
The catch that makes access control real
Omni Gateway can only enforce policy on traffic that actually passes through it. Your single Anthropic API key lives inside the wrapper — so if a consumer can reach the wrapper directly, they ride your key with zero consumer-level control. Therefore: the Agent Card must advertise the gateway-fronted URL, and the raw wrapper must be locked down so only the gateway can reach it. Same "don't let clients bypass the proxy" discipline as classic API management — now for agent traffic.

Hands-on — scaffold the A2A wrapper

You'll build the front door in Python, reusing the A2A primitives you already verified in L47. The wrapper's job is tiny: accept an A2A task, hand its text to the Claude agent, return the result as a completed task. The Claude call is left as a TODO for you to wire — that's the learning.

The MuleSoft-native alternative (no Python)
Everything above can be a Mule flow instead: the A2A Connector v2.0.0 (Exchange) provides the a2a:task-listener + Agent Card (as you saw in L48); the flow body calls the Anthropic API via HTTP Request. Then it's deployed on Omni Gateway and published to the Registry through the platform — the governed, no-custom-server path. Same three steps: card → registry → gateway.

The SE talk track

"You've built a great agent on Claude — now other teams want to use it, and that's where it gets risky. Right now the only way in is your raw Anthropic key, which authenticates you to Anthropic but says nothing about which of your consumers is calling — no per-team limits, no audit, no way to cut one off. Put a thin A2A front door on it, register its card in our Agent Registry so it's discoverable and reusable across the org, and route every inbound call through Omni Gateway. Now each consumer is authenticated, rate-limited, and logged before a single token of your Anthropic quota is spent — and if you ever swap Claude for another model, consumers never notice, because they depend on the card, not on Anthropic. It's the same 'publish it once, govern it centrally' play you already run for APIs — the endpoint just happens to be an agent."
